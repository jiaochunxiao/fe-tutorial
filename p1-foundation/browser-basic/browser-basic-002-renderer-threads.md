# 浏览器基础之渲染进程的线程构成

## 从「JS 死循环时页面还能滚动」说起

上一篇埋了一个看似矛盾的现象：

```js
// 页面上跑这段代码——主线程彻底卡死
while (true) {}

// 神奇的是：页面可能【依然能滚动】！
// （某些情况动画甚至会动——但事件、JS、交互全部失灵）
```

「JS 单线程」的页面怎么会「半死不活」？答案：**渲染进程内部是多线程的**——JS 只霸占其中一条（主线程），滚动/合成等可以跑在别的线程上。⭐⭐ 理解线程分工，才能解释「长任务卡什么不卡什么」——这是性能优化与事件循环的物理地基。

## 现象与直觉解释

渲染进程（一个标签页的「车间」）里的主要线程班子：

```
┌──────────────── 渲染进程 ────────────────┐
│ ① 主线程（Main Thread）★ 一人分饰多角：      │
│    JS 执行 + DOM/样式/布局/绘制计算 + 事件循环│
│ ② 合成线程（Compositor Thread）            │
│    把图层拼成帧；可以独立响应滚动 ⭐          │
│ ③ 光栅线程（Raster Threads，一组）          │
│    把绘制指令变成像素（GPU 加速）            │
│ ④ IO 线程：与浏览器进程的 IPC 收发           │
└───────────────────────────────────────────┘
```

直觉：**主线程是「全能但只有一个的师傅」**——HTML 解析、JS、样式、布局全归他；合成线程是「只管拼图的助手」——一旦图层的绘制指令准备好了，滚动这类纯合成工作无需惊动主线程。

## 深入原理

### 一、主线程：为什么 JS 与渲染互斥 ⭐⭐

主线程身兼两职：**执行 JavaScript** 与 **GUI 渲染（DOM/样式/布局/绘制计算）**——两者**互斥**：

```js
// 渲染要等 JS：JS 可能改 DOM（改完再算布局才不是白算）
// JS 要等渲染：渲染中的页面不能被半路改 DOM
// → 同一条线程上排队执行 —— 「JS 执行时页面不更新、渲染时 JS 不跑」
```

这就是「长任务卡页面」的物理原因：一个 200ms 的 JS 任务让主线程无暇渲染——掉帧（60fps 每帧只有 16.7ms 预算）；「白屏死循环」则是极端形态。

推论（性能篇的地基）：**性能优化的本质大多是「把工作从主线程挪走或切碎」**——挪给 Worker、挪给合成线程（transform 动画）、或切成 <50ms 的碎片（长任务拆分）。

### 二、合成线程：滚动的「绿色通道」⭐⭐

页面滚动时，内容在屏幕上移动——理论上需要「重新画」。但浏览器有个优化：**如果图层已经光栅化好，滚动只是把现成图块挪位置拼贴**——这活合成线程自己就能干，**完全不经过主线程**。

```
滚动的两种命运：

① 纯合成滚动（compositor scrolling）：
   页面无 JS 监听 scroll 干预、图层已备好
   → 合成线程直接拼贴 ✅ 丝滑 60fps（主线程卡死也照样滚——开篇之谜）

② 主线程参与滚动：
   页面有 scroll 事件监听要跑、有 position:fixed 要重算、懒加载逻辑…
   → 每帧都要回主线程 ⚠️ 主线程一忙，滚动就卡
```

这个分叉直接指导实践：**scroll 监听里别做重活**（改样式触发布局的监听器会让滚动「降级」为主线程路径）；`transform` 动画走合成线程所以丝滑（《rendering-003》专篇展开）。

### 三、IO 线程与「跨进程的异步」⭐

网络请求的完整路径：

```
JS: fetch(url) ──请求──▶ IO线程 ──IPC──▶ 浏览器进程 ──网络进程──▶ 服务器
                （主线程立刻返回 promise，继续干别的）
服务器响应 ──网络进程──▶ IO线程 ──任务队列──▶ 主线程的事件循环里回调你
```

「异步」的物理实现：**耗时的活根本不在渲染进程的主线程上干**——网络在专门进程、定时器由调度者托管，**完成后把回调排进主线程的任务队列**，等主线程闲了再执行。这就是事件循环（《js-async-005》）的线程级真相。

### 四、定时器的精度真相 ⭐

```js
setTimeout(fn, 0);   // 实际最小 ~4ms（嵌套 5 层后）——规范允许的下限
setTimeout(fn, 16);  // 主线程忙时可能 50ms 后才跑 —— 排队
requestAnimationFrame(fn);  // 对齐「下一帧渲染」——动画的正确选择（《rendering-004》）
```

setTimeout 的回调也是「进任务队列等主线程」——**它不保证准点，只保证不早于**。动画用 rAF 而非 setTimeout 的根本原因：rAF 的回调时机与渲染管线对齐。

## 回看开篇

死循环时还能滚动的答案：死循环霸占的是**主线程**；若页面满足「纯合成滚动」条件（图层已备、无主线程干预），**合成线程**独立完成滚动拼贴——所以「能滚但不能点」：点击要跑事件回调（主线程），滚动只要挪图块（合成线程）。**线程分工决定了「死」的范围。**

## 实战延伸

**1. 面试答题骨架**：「渲染进程内主线程负责 JS 执行与 DOM、样式、布局、绘制等 GUI 工作，两者互斥排队——这是长任务掉帧与 JS 单线程说法的物理来源；合成线程负责图层拼贴，已光栅化的页面滚动可完全在合成线程完成，不惊动主线程，所以主线程卡死时滚动可能依然流畅，但一旦页面监听 scroll 并干预样式，滚动就降级为主线程参与；网络等耗时操作在独立进程/线程完成，回调经任务队列回到主线程的事件循环，setTimeout 只保证不早于目标时间。」

**2. 亲手观测**：Performance 面板录制滚动——Main 轨道（主线程）空闲而 Frames 稳定 60fps = 纯合成滚动；Main 里出现密集的 scroll 回调与紫色布局条 = 主线程参与路径。

**3. 快手辨析**：`Web Worker` 是渲染进程里的**另一条线程**（可算不可摸 DOM——DOM 只属于主线程）；`requestIdleCallback` 仍是主线程（只是排空闲档）。

## 图解总结

```
渲染进程
┌───────────────────────────────────────────┐
│ 主线程（唯一全能）: JS ⇄ DOM/样式/布局/绘制 ──互斥排队→ 长任务=掉帧
│   └ 事件循环：任务队列 ← IO线程/定时器/网络进程的回调
│ 合成线程: 图层拼贴 —— 纯合成滚动 ⭐（主线程死了也滚）
│ 光栅线程组: 指令→像素（GPU）
│ IO线程: 与浏览器进程 IPC
└───────────────────────────────────────────┘
推论: 优化 = 挪走（Worker/合成）或切碎（<50ms 长任务）
```

## 总结

- 主线程一人分饰 JS 与 GUI 两角，互斥排队——长任务卡页面的根源；
- 合成线程可独立滚动（纯合成路径）；scroll 监听干预会让滚动降级主线程；
- 网络/定时器在别处完成，回调进任务队列等主线程——异步的线程级真相；
- setTimeout 只保证不早于；动画对齐帧用 rAF；
- Worker 是渲染进程的另一线程，能算不能摸 DOM。

**面试一句话回答**：渲染进程内是多线程的——主线程同时负责 JavaScript 执行与 DOM 解析、样式计算、布局、绘制等 GUI 工作，两者互斥排队，这就是长任务导致掉帧以及 JS 被称为单线程的物理原因；合成线程负责图层合成，已光栅化的页面滚动可以完全由合成线程独立完成、不经过主线程，所以主线程死循环时滚动仍可能流畅，但点击等事件回调必须回主线程因此失灵；网络请求在网络进程完成、定时器由调度托管，完成后回调进入任务队列由主线程的事件循环择机执行——setTimeout 只保证不早于指定时间触发，动画应使用与渲染帧对齐的 requestAnimationFrame。

## 思考题

1. 页面用了 `position: sticky` 吸顶，滚动为什么可能从「合成线程路径」降到「主线程路径」？（提示：粘性布局需要每帧重算位置）
2. 主线程死循环时，`setTimeout` 回调、scroll 位置、CSS transform 动画、图片加载完成——各自还能进行吗？逐个分析所在线程。
3. 为什么「把 scroll 回调里的逻辑改成 rAF 批处理」能改善滚动性能？从「每帧回主线程次数」解释。
4. 开放讨论：浏览器为什么不把 DOM 操作也做成多线程安全（像 Java 的 SWT）——从「一致性成本 vs 收益」谈谈单线程 GUI 模型的取舍。
