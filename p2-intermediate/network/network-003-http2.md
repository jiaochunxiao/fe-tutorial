# 网络与浏览器之 HTTP/1.1 的问题与 HTTP/2

## 从一个「祖传优化三板斧」说起

老前端面试爱问：「首屏慢，你有哪些加载优化手段？」标准答案里常有三板斧：**雪碧图（合并小图标）、内联资源、域名分片（把资源分散到 static1/static2/static3…）**。

追问一句：「**为什么**这些手段有效？现在还需要吗？」——答案全在 HTTP/1.1 的设计缺陷里。而 HTTP/2 出现后，这三板斧有的失效、有的甚至**有害**。⭐⭐ HTTP/2 的动机与改进是高频考点，也是理解现代前端资源加载策略的前提。

## 现象与直觉解释

HTTP/1.1 的世界：「**一个 TCP 连接上，同一时刻只能跑一个请求**」。浏览器等不及，只能开多条连接（每域名上限 6 条）。于是：

```
连接1: [请求A ████][等待响应A][请求C ████]...
连接2: [请求B ███][等待响应B][请求D ███]...
（6 条连接并行 = 6 车道公路，每条车道一次只能过一辆车）
```

- 请求多 → 排队 → 慢。所以把 100 张小图合成 1 张雪碧图（请求少了）；把 CSS 内联进 HTML（又少一个）；开 3 个域名（车道从 6 变 18）。
- 这些都是**绕过协议缺陷的工程 hack**，HTTP/2 的目标就是从协议层消灭排队。

## 深入原理

### 一、HTTP/1.1 的三大缺陷 ⭐

**缺陷 1：应用层队头阻塞（HOL blocking）**

一个连接上必须「请求-响应-请求-响应」串行，前面的响应不到，后面的请求干等。历史上尝试过「管道化（pipelining）」——把请求连续发出——但响应仍须**按序返回**，第一个慢响应照样堵死整队，且中间件支持极差，被浏览器默认关闭。

**缺陷 2：头部冗余**

HTTP/1.1 头部是**纯文本**且每次全量发送。Cookie 动辄几 KB——每个请求都背着同样的几 KB 明文头部重复传输。

**缺陷 3：无优先级**

服务器不知道哪个资源更重要（CSS vs 图片），只能先来后到，关键渲染路径（关联《performance-003 加载优化》）无从谈起。

### 二、HTTP/2 的四大改进 ⭐⭐

**改进 1：二进制分帧（Binary Framing）——一切的基石**

报文不再是大段文本，而是拆成一个个**二进制帧（frame）**：帧头标明「属于哪个流（stream）、什么类型（HEADERS/DATA…）、多长」。

```
HTTP/1.1（文本流）:   ┌──────── 完整报文 A ────────┐┌──────── 完整报文 B ────────┐  必须整块、按序

HTTP/2（帧交织）:     [A头帧][B头帧][A数据帧0][B数据帧0][A数据帧1]...
                      同一连接上，多个流的帧自由交错、按流重组 ✅
```

**改进 2：多路复用（Multiplexing）**——一条 TCP 连接上，无数个「流」并行交错传输，互不阻塞：

```
                    一条 TCP 连接
流1(HTML)   ▓▓▓░░▓▓▓░░░
流2(CSS)    ░░▓▓▓▓░░▓▓░     ▓=帧  ░=其他流的帧
流3(JS)     ░▓▓░░▓▓▓░░▓     接收端按流 ID 重组出完整报文
```

- 6 连接限制作废：**单连接即可填满带宽**；
- 队头阻塞（应用层）消灭：流 3 的响应慢，不挡流 1、2 的帧。

**改进 3：头部压缩（HPACK）**

客户端与服务端各维护一张**头部索引表**（静态表 + 动态表），重复的头部只传索引号。`Cookie: sid=xxx…2KB` 第二次起可能只传几十字节的差量——对 REST 高频接口收益巨大。

**改进 4：服务器推送（Server Push）与流优先级**

服务器可以在请求 HTML 时「顺手」推送它预判你要的 CSS/JS（PUSH_PROMISE 帧）；流可以声明权重与依赖（CSS 高优先、图片低优先）。——注：推送因缓存匹配困难，Chrome 已移除对它的支持，**作为概念了解即可**；优先级思想延续到了 HTTP/3 的 Extensible Priorities。

### 三、必须知道的遗留问题：TCP 层队头阻塞 ⭐

HTTP/2 只消灭了**应用层**的排队，但所有流共享一条 TCP 连接，而 TCP 保证**字节流的有序交付**：

```
HTTP/2 一条 TCP 连接上跑着流1、流2、流3
某一时刻丢了一个 TCP 包 → TCP 必须等重传补齐才能继续上抛字节
→ 三个流「全都被这一个丢包卡住」——队头阻塞下移到了 TCP 层
```

连接复用越充分，单点丢包的杀伤面越大（弱网下 HTTP/2 有时反而不如 1.1 的多连接）——这是 HTTP/3 换掉 TCP 的直接动因（下一篇）。

### 四、旧三板斧在新协议下的命运

| 老优化 | HTTP/1.1 下的理由 | HTTP/2 下 |
|---|---|---|
| 雪碧图 | 减少请求次数 | 收益骤减；小图直接 HTTP 缓存 + 按需加载更好，SVG/图标字体/内联依然有效（省的是请求数与渲染便利） |
| 域名分片 | 增加连接车道 | **有害**：多域名 = 多次 DNS/TCP/TLS 握手 + 破坏 HPACK 共享（连接少了压缩才有效） |
| 内联 CSS/JS | 省请求 | **需重估**：内联导致无法独立缓存；权衡后「关键 CSS 内联、其余外链」仍是主流 |

结论：**协议演进会重写优化手册**——做优化先看协议版本（DevTools Protocol 列的 `h2`/`h3`）。

## 回看开篇

三板斧有效的根源是「每车道一次一辆车」的串行模型；HTTP/2 用二进制分帧 + 多路复用把公路改成了「单车道、无数小车自由穿插」——域名分片这类「多修路」的 hack 自然作废。**先看协议再谈优化**。

## 实战延伸

**1. 怎么确认网站在用 HTTP/2**：DevTools → Network → 右键列头勾选 Protocol，显示 `h2` 即 HTTP/2、`h3` 即 HTTP/3。

**2. HTTP/2 下的新优化方向**：请求数不再是主要矛盾，**单请求体积与关键路径优先级**成为重点——代码分割按「路由」而非「碎到函数」、`fetchpriority`/preload 标注关键资源（关联《performance-003》）。

**3. 面试问答模板**：「HTTP/1.1 有应用层队头阻塞、头部冗余、无优先级三大问题，历史优化是雪碧图/内联/域名分片；HTTP/2 用二进制分帧实现单连接多路复用、HPACK 头部压缩与流优先级解决之；但所有流共享一条 TCP 连接，丢包会阻塞全部流——队头阻塞下移到 TCP 层，这正是 HTTP/3 改用 QUIC 的原因。」

## 图解总结

```
HTTP/1.1: 6条连接 × 每条串行         HTTP/2: 1条连接 × 帧交错
c1: A→A→C→C                          ═══ TCP 连接 ═══
c2: B→B→D→D                          [A帧|B帧|A帧|C帧|B帧|A帧]
c3: …(域名分片再开6条)                 流A▓ 流B▒ 流C░ 并行重组
每条车道一次一辆 → 排队/绕路           应用层无排队；
                                     ⚠ 丢一个TCP包 → 整条连接所有流等待重传
```

## 总结

- HTTP/1.1 三缺陷：应用层队头阻塞、文本头部冗余、无优先级；催生雪碧图/内联/域名分片三大 hack；
- HTTP/2 四改进：二进制分帧（基石）、多路复用（单连接并行流）、HPACK 头压缩、流优先级/服务器推送；
- 多路复用消灭了应用层排队，但**队头阻塞下移到 TCP 层**（单连接丢包全流遭殃）；
- 协议版本重写优化手册：域名分片在新协议下有害，优化重心转向单请求体积与优先级。

**面试一句话回答**：HTTP/1.1 因为连接上请求串行存在应用层队头阻塞、纯文本头部冗余且无优先级，所以有雪碧图、内联、域名分片这些绕路优化；HTTP/2 通过二进制分帧把报文拆成带流 ID 的帧，在一条 TCP 连接上多流交错复用，配合 HPACK 头部压缩和流优先级解决了以上问题；但 TCP 字节流的有序交付让丢包阻塞所有流，队头阻塞下移到传输层——这正是后来 HTTP/3 用基于 UDP 的 QUIC 重写传输层的动机。
