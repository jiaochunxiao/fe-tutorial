# 渲染原理之事件循环与渲染的交错

## 把两张图拼成一张（本系列的「大一统」）

课程里有两张著名的图：

```
图A（js-async-005）: 任务 → 微任务 → （可能）渲染 → 下一个任务
图B（rendering-001/004）: rAF → Style → Layout → Paint → Composite
```

**本篇回答**：它们怎么拼起来？渲染「可能发生」的判定是什么？长任务如何杀死帧？⭐⭐⭐ 这是渲染与异步两大知识线的合流点——理解它，前端性能的「为什么」全部打通。

## 现象与直觉解释

完整的一轮事件循环（拼图版）⭐⭐⭐：

```
① 取一个任务（宏任务）执行
② 清空微任务队列（含新产生的）
③ 【渲染机会判定】—— 满足才渲染：
   ├── 距上帧已满一个 vsync 间隔？
   ├── 页面可见？（后台标签跳过）
   └── 有变化？（无脏标记也跳过——rAF 仍可能被跳过 ⭐）
④ 渲染步骤（渲染机会成立时）：
   rAF 回调们 → Style → Layout → Paint → Composite
⑤ 回到 ①
```

**关键认知**：渲染不是每轮循环都发生——**任务与微任务可以连续多轮执行而不渲染**（如果还没到 vsync 或没有变化）。

## 深入原理

### 一、「渲染机会」的三个判定 ⭐⭐

```js
// 判定1: 时间（vsync 节拍）
//   60Hz 屏 ≈ 16.7ms 一拍。任务太快做完（两轮循环只用 3ms）→ 不渲染（没到点）
// 判定2: 可见性
//   display:none 的 iframe、后台标签 → 不渲染（但任务/微任务照跑）
// 判定3: 脏标记
//   没有任何样式/DOM 变化 → 浏览器可跳过渲染步骤（省电）
//   ⭐ 推论: rAF 不保证每 16.7ms 执行一次——无渲染机会就无 rAF
```

### 二、长任务如何杀死帧（帧预算模型）⭐⭐⭐

```
帧预算（60Hz）= 16.7ms，其中：
  [任务+微任务] [rAF] [Style] [Layout] [Paint] [合成] [空闲]
                                     ↑ 全部跑在【同一个主线程】（browser-basic-002）

长任务（>50ms）的杀伤路径：
  占用主线程 40ms ──▶ 本帧预算爆 ──▶ 渲染机会被跳过（下一拍才渲）
  ──▶ 用户看到：掉帧（动画跳变）、输入延迟（点击回调排队）──▶ INP/LCP 双杀
```

**这就是 INP 优化的总原理**：把长任务拆碎（<50ms），每块之间把主线程还给「渲染与交互」：

```js
// 让路的现代姿势（任务拆分）
async function chunked(items) {
  for (let i = 0; i < items.length; i++) {
    process(items[i]);
    if (i % 100 === 0) await scheduler.yield();   // 主动让出（新 API）
    // 兼容写法: await new Promise(r => setTimeout(r))（宏任务让路，粒度粗）
  }
}
```

### 三、微任务的特殊地位（渲染前的最后冲刺）⭐⭐

```
微任务在【每个任务之后、渲染之前】清空：
  await 后续、Promise.then、queueMicrotask —— 全在渲染前完成
推论1: 「同步代码 + await 链」里改样式 → 同帧生效（微任务仍在渲染前）⭐
推论2: 微任务死循环 = 页面冻结（永远到不了渲染步骤）
       while(true) queueMicrotask(...) —— 比 JS 死循环更彻底（连紧急任务都进不来）
```

### 四、三张高频时序题的统一解法 ⭐⭐

用拼图版模型推导（不再背答案）：

```js
// 题1: setTimeout(fn,0) 与 rAF 谁先？
// → 下一轮循环的 ①任务 先于 ④渲染的 rAF（同一拍内任务在前）

// 题2: promise.then 里改样式，与 rAF 里改样式谁先「生效」？
// → 微任务在本帧 ②、rAF 在本帧 ④ —— 都在本帧渲染前，同帧生效（次序: then 改的被 rAF 的覆盖）

// 题3: 为什么 scroll 回调里改样式容易掉帧？
// → scroll 事件作为任务执行（①），你的改样式触发 Style→Layout 排进本帧 ④
//    若回调太重 → 帧预算爆 → 掉帧（performance-005 的 rAF 合帧是解法）
```

### 五、帧率、掉帧与「半帧」的工程感知 ⭐

```
DevTools Performance 的 Frames 轨:
  绿条满高 = 60fps；矮绿 = 半帧渲染（部分更新）；红条 = 掉帧
稳定的 30fps（均匀红绿交替） 优于 波动的 45fps（节奏乱）—— 动画感知的关键是【稳定】
（引出: 故意限帧到 30（隔帧渲染） vs 波动 45 的选择——游戏领域的经典权衡）
```

## 回看开篇

两张图的拼接处是「渲染机会判定」：任务→微任务是 JS 世界的节拍，vsync 是显示世界的节拍，浏览器在每个循环间隙检查「要不要把 JS 世界的成果渲染出去」——**两个节拍的协调器就是事件循环**。长任务、INP、rAF 时序、scroll 掉帧……全部性能现象都发生在这条拼接缝上。

## 实战延伸

**1. 面试答题骨架**：「每轮事件循环先执行一个任务并清空全部微任务，然后进行渲染机会判定——距上帧满一个刷新周期、页面可见且有变更三者满足才进入渲染步骤：执行 rAF 回调后走样式、布局、绘制、合成。渲染不是每轮都发生，任务密集时可能连续多轮不渲染，因此 rAF 的频率不严格等于刷新率。所有阶段共享主线程，超过五十毫秒的长任务会吃掉帧预算造成掉帧与输入延迟，解法是任务拆分与主动让路。微任务位于渲染之前，因此 await 链中的样式修改同帧生效，而微任务死循环会彻底冻结渲染。」

## 图解总结

```
一轮循环（拼图版）:
 ①任务 → ②清微任务 → ③渲染机会?(vsync到点? 可见? 有脏?) ─否→ 下一轮
                              │是
                              ▼
        ④rAF → Style → Layout → Paint → Composite ═▶ 上屏

帧预算 16.7ms: [任务][微任务][rAF][管线][空闲] 全在主线程
长任务>50ms ──▶ 跳拍掉帧 + 输入排队 ──▶ INP/LCP 双杀
解法: scheduler.yield/拆任务 │ rAF合帧(scroll) │ 能合成不主线程
微任务: 渲染前清空(同帧生效) │ 微任务死循环=连渲染机会都没有
```

## 总结

- 拼图版循环：任务→微任务→渲染机会判定→rAF→管线→合成；
- 渲染三判定：vsync 到点、可见、有脏——rAF 频率≠刷新率；
- 帧预算 16.7ms 全程主线程——长任务双杀 INP/LCP，拆分与让路是解；
- 微任务在渲染前清空：await 链改样式同帧生效；微任务死循环冻结一切；
- 稳定帧率优于波动帧率。

**面试一句话回答**：每轮事件循环先执行一个宏任务并清空整个微任务队列，随后浏览器进行渲染机会判定——只有距上一帧满一个刷新周期、页面可见且有实际变更三个条件满足时才进入渲染步骤，依次执行 requestAnimationFrame 回调、样式计算、布局、绘制与合成。渲染不是每轮循环都会发生，任务密集时可能连续多轮跳过渲染，所以 rAF 的执行频率并不严格等于屏幕刷新率。所有这些阶段共享一条主线程，十六点七毫秒的帧预算被长任务吃掉就会跳帧并让输入排队，这是 INP 与 LCP 恶化的共同根源，解法是拆分长任务并用 scheduler.yield 主动让路；微任务位于渲染之前，因此 await 链中的样式修改能在同一帧生效，而微任务死循环会让渲染机会永远无法到来。

## 思考题

1. 设计实验证明「渲染机会的跳过」：连续快速同步执行多轮 setTimeout(0)（每轮 1ms），观察 rAF 触发频率。
2. `await new Promise(r => setTimeout(r))` 与 `scheduler.yield()` 的让路粒度差异？（宏任务边界 vs 可能在帧内更细的让出点）
3. 用拼图模型推导：为什么 `MutationObserver` 回调（微任务）里改 DOM 不会无限循环地阻塞渲染？（变更→新微任务→渲染前清空→有机会渲染——除非你持续变更）
4. 开放设计：视频弹幕渲染（持续高频更新 + 不许掉帧）——合成层 + rAF 批量 + Canvas 合并的三方案对比。
