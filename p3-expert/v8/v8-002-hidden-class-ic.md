# V8 之隐藏类与内联缓存

## 从「两个形状相同的对象，访问速度差十倍」说起

```js
function Point(x, y) { this.x = x; this.y = y; }
const a = new Point(1, 2);
const b = new Point(3, 4);
b.description = '额外属性';     // ⚠️ 多塞了一个

function getX(p) { return p.x; }
loop: getX(a);   // 快 —— 走了内联缓存的快速路径
loop: getX(b);   // 慢得多 —— 隐藏类不同，缓存失效
```

JS 对象是「动态字典」——按直觉，`p.x` 应该查哈希表（慢）。但 V8 让 99% 的属性访问**快如固定偏移的内存读取**——靠的是两大优化搭档：**隐藏类（Hidden Class / Map）+ 内联缓存（Inline Cache, IC）**。⭐⭐⭐ 这是「JS 为什么能这么快」的核心机密，也是「什么样的代码对引擎友好」的判断依据。

## 现象与直觉解释

**问题**：静态语言（C++）访问 `obj.x` = 「对象基地址 + 固定偏移」一条指令；JS 的对象可以随时增删属性——**偏移量没法固定**。

**V8 的答案**：给每个对象偷偷挂一个「形状描述」（隐藏类），记录「属性名 → 偏移量」的映射：

```
隐藏类 C0: { x: offset 0, y: offset 8 }   ← Point 实例共享的形状
对象 a: [ Map=C0 ][ x=1 ][ y=2 ]          ← 对象头里存着"我是 C0 形状"
```

**共享的关键**：相同方式构造的对象共享同一个隐藏类——`p.x` 的偏移就可以按「形状 + 属性名」确定。

### 转移链（Transition Chain）：形状是怎么长出来的

```
new Point() 时：
  C0 (空) ──加 x──▶ C1 {x:0} ──加 y──▶ C2 {x:0, y:8}
  a、b 都沿 C0→C1→C2 长出来 → 共享 C2 ✅

b.description = '…' 时：
  C2 ──加 description──▶ C3（新形状）   → b 独自变到 C3，与 a 分道扬镳 ❌
```

## 深入原理

### 一、内联缓存（IC）：把「查找」变成「记住」⭐⭐⭐

有了隐藏类，访问 `p.x` 仍要「读 Map → 在形状里查 x 的偏移」。IC 更进一步——**把结果缓存到访问点**：

```
function getX(p) { return p.x; }
      │
      ▼ 第一 次执行：慢路径（查 C2 得 offset=0），并把 (形状C2, offset=0) 存进
      ▼        这行代码的【内联缓存槽】
      ▼ 以后执行：① 读 p 的 Map === C2？（一次比较）
                ② 命中 → 直接按缓存的 offset 取值 —— 两条指令 ⚡
                ③ 不命中 → 退回慢路径 + 尝试更新缓存（或进入 megamorphic 放弃）
```

IC 的四态（按缓存内容分级）⭐：

| 状态 | 含义 | 速度 |
|---|---|---|
| uninitialized | 还没执行过 | — |
| monomorphic | 只见过 1 种形状 | 最快 ⭐ |
| polymorphic | 见过 2~4 种 | 需小表轮询 |
| megamorphic | >4 种，放弃缓存 | 走通用慢路径 ❌ |

**开篇实验的解释**：`getX(a)` 一直是 monomorphic（只见过 C2）；掺入 `b`（C3）后变 polymorphic，再多形状就 megamorphic——属性访问退化为通用查找，「十倍差距」由此而来。

### 二、破坏优化的四大写法（「引擎不友好」清单）⭐⭐⭐

```js
// ① 属性添加顺序不同 → 不同转移链 → 不同形状
const o1 = {}; o1.a = 1; o1.b = 2;
const o2 = {}; o2.b = 2; o2.a = 1;    // ❌ 形状与 o1 不同（a、b 偏移互换）

// ② 动态删除属性 → delete 破坏形状（进入慢属性模式）
delete o1.a;                           // ❌ 尽量用置 null/undefined 替代

// ③ 中途塞新属性（开篇的 b.description）
// ✅ 正解：构造函数里一次性声明全部属性（哪怕初始 undefined）

// ④ 同一函数接收大量不同形状的对象
render(point); render(circle); render(user); …  // ❌ IC 打成 megamorphic
// ✅ 正解：同类数据统一构造路径 / TS 类型约束形状稳定
```

### 三、「字典模式」：什么时候连隐藏类都没有 ⭐

```
过度动态的对象会被 V8 判定"放弃治疗"→ 直接用属性字典（慢模式）：
  - delete 过多次
  - 属性特别多（几十上百个）且乱序添加
  - 动态键名拼装（obj[keyVar] 逐个塞）
（这也解释了「用对象当 Map 用」的隐形代价 —— es6-007 的选型理由+1）
```

### 四、验证工具：%HaveSameMap ⭐

```js
// Node --allow-natives-syntax
function Point(x, y) { this.x = x; this.y = y; }
const a = new Point(1, 2), b = new Point(3, 4);
%HaveSameMap(a, b);          // true ✅ 同形状
b.z = 1;
%HaveSameMap(a, b);          // false ❌ 形状分裂
%DebugPrint(a);              // 打印对象的 Map/形状详情（调试神器）
```

## 回看开篇

十倍差距的完整机制链：`b.description = …` 让 b 沿转移链走到新形状 → `getX` 的内联缓存从 monomorphic（一次比较直取）跌到 polymorphic（查小表）→ 多形状混杂后 megamorphic（通用查找）——**对象形状的稳定性决定了属性访问的快慢**。

## 实战延伸

**1. 面试答题骨架**：「V8 用隐藏类描述对象的属性布局——相同构造路径的对象沿同一条转移链共享形状，属性名映射到固定偏移；内联缓存再把『形状 → 偏移』的结果缓存到访问点，之后只需比较对象形状命中即按偏移直取。缓存分 monomorphic、polymorphic、megamorphic 四态，形状越单一越快。因此引擎友好的写法是构造函数一次性声明全部属性、保持添加顺序一致、避免 delete 与动态键、让函数稳定接收同类形状——相反的写法会造成形状分裂与缓存降级，甚至触发字典慢模式。」

**2. 工程清单**（把理论变成规范）：数据模型统一工厂/构造函数；不 delete（置空）；批量字段一次初始化；热路径函数别混传异构对象。

## 图解总结

```
隐藏类(形状):  C0 ─a─▶ C1 ─b─▶ C2{x:0,b:8}      转移链
对象头:        [Map=C2][a][b]                     同构造路径 → 共享形状

内联缓存(IC):  访问点缓存 (形状, 偏移)
  执行: p.Map === C2 ? 直接 [p+offset] ⚡ : 慢路径+更新缓存
  四态: mono(1形状,最快) → poly(2-4) → mega(>4,通用查找)

破坏王: 顺序不同 │ delete │ 中途加属性 │ 异构混传
       → 形状分裂 / 缓存降级 / 字典模式
正解: 构造函数一次声明全部 │ 统一构造路径 │ 用置空替代delete
```

## 总结

- 隐藏类=对象形状（属性→偏移），同构造路径共享，沿转移链演化；
- IC 把形状→偏移缓存在访问点：比较一次形状、按偏移直取；
- IC 四态：形状越单一越快，megamorphic 退化为通用查找；
- 破坏王：属性顺序不一、delete、中途加属性、异构混传；
- 引擎友好写法：一次声明全部属性、统一构造路径、置空替代删除。

**面试一句话回答**：V8 为每个对象维护隐藏类（Map）描述属性布局，相同构造路径的对象沿同一条转移链共享形状，属性名对应固定的内存偏移；内联缓存进一步在属性访问的代码点缓存「形状到偏移」的映射，之后执行时只需比较对象形状、命中即按偏移直接读取内存。缓存状态从 monomorphic 到 polymorphic 再到 megamorphic 逐级降速——函数只接触一种形状时最快、超过四种则退回通用查找。因此引擎友好的写法是在构造函数里一次性声明所有属性、保持属性添加顺序一致、避免 delete 与动态键名、避免让同一函数接收大量不同形状的对象，否则会造成形状分裂与缓存降级，甚至让对象落入纯字典的慢速模式。
