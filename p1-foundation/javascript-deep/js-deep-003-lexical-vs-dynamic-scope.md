# JavaScript 深入之词法作用域与动态作用域

## 从一个「违反直觉」的输出说起

```js
var value = 1;

function foo() {
  console.log(value);
}

function bar() {
  var value = 2;
  foo();
}

bar(); // 输出 1，而不是 2
```

`foo` 明明是在 `bar` **里面**被调用的，而 `bar` 里就有一个 `value = 2`。按「就近原则」的直觉，`foo` 打印的应该是 2 才对——但它打印的是 1。

如果你的第一反应也是 2，说明你下意识用的是**动态作用域**的思维模型；而 JavaScript 用的是另一套。⭐ 这是一道流传极广的面试题，考的就是这两种作用域模型的区别。

## 现象与直觉解释

世界上存在两种作用域模型：

- **词法作用域（lexical scope，也叫静态作用域）**：函数能访问哪些变量，在**写代码（函数定义）的时候**就确定了。关注点是——函数在哪里**声明**。
- **动态作用域（dynamic scope）**：函数能访问哪些变量，在**运行（函数调用）的时候**才确定。关注点是——函数在哪里**调用**。

JavaScript 是**词法作用域**。一些经典脚本语言（如 bash、Emacs Lisp）采用的是（或接近）动态作用域。

用两套模型分别推演开篇代码：

- **词法作用域（JS 的实际行为）**：`foo` 定义在全局，查找 `value` 的路径是「foo 内部 → 全局」，路径里根本没有 `bar`，所以找到全局的 `1`。
- **动态作用域（假设）**：`foo` 在 `bar` 内被调用，查找路径是「foo 内部 → 调用者 bar → 全局」，在 `bar` 里就命中 `2`。

直觉解释到这里就通了。但要真正吃透，得看引擎是怎么落实「定义时确定」的。

## 深入原理

### 一、「定义时确定」的机制：[[Environment]]

上一篇《js-deep-002 变量对象》讲过，上下文创建阶段引擎会登记变量。本篇的关键在另一个机制：

> ECMAScript 规范规定，每个函数对象创建时，都会通过内部槽 **`[[Environment]]`** 保存「函数定义时所处词法环境」的引用。

也就是说，函数一出生，就自带一份「出生地证明」。无论它后来被传到哪里、在哪里被调用，查找外层变量时都认这份证明——沿着**定义处**的环境链往外找，而不是沿调用关系找。

这就是「词法（lexical）」一词的本意：**lexical 意为「与文本/书写相关」**，即作用域关系由代码的书写结构决定，编译阶段就能静态分析出来。

### 二、对照推演：两套模型下的查找过程

```
词法作用域（JavaScript）：
  foo.[[Environment]] ──▶ 全局环境 { value: 1 }
  执行 foo：foo 自身环境（无 value）→ 全局环境（命中 1）
  bar 的环境？——根本不在 foo 的查找链上

动态作用域（假设模型）：
  调用栈：全局 → bar → foo
  执行 foo：foo 自身环境（无 value）→ 沿调用栈找到 bar 的环境（命中 2）
```

同一份代码，两套模型给出不同答案——差异只在于**「往外找」的方向**：一个沿定义的嵌套结构，一个沿运行时的调用栈。

### 三、为什么主流语言都选词法作用域

动态作用域并非「错误」设计，只是权衡不同：

| 维度 | 词法作用域 | 动态作用域 |
|---|---|---|
| 可读性 | 看函数源码就知道能访问什么 | 得看遍所有调用点才能确定 |
| 可预测性 | 调用环境不影响结果 | 同一函数在不同调用栈里行为不同 |
| 静态分析 | 编译期可做检查与优化 | 几乎只能运行时决定 |
| 副作用 | 封装性好 | 调用者会「意外地」影响被调函数 |

正因为词法作用域可以被静态分析，引擎才能放心地做变量查找快速路径、构建工具才能做 tree-shaking、IDE 才能准确补全。这也是为什么 ES Module（强制静态结构）比 CommonJS 更利于优化——静态可分析是整个现代前端工程化的地基之一。

### 四、两个「破坏者」：eval 与 with

JavaScript 里有两个语法能欺骗词法作用域：

**1. eval——在当前位置注入代码**

```js
function foo(str, a) {
  eval(str); // 这行代码在运行时"长出了"一个 b
  console.log(a, b);
}

foo('var b = 3;', 1); // 1 3，而不是 ReferenceError
```

`eval` 里的声明仿佛写在了 `foo` 内部，词法结构在运行时被改变了。后果：**引擎无法再假设 foo 的作用域是静态的**，只能放弃对该函数的部分优化。严格模式下，`eval` 会拥有自己的作用域，不再污染外层。

**2. with——把对象当作作用域**

```js
var obj = { a: 1, b: 2 };

with (obj) {
  a = 3;   // 修改的是 obj.a
  c = 4;   // obj 没有 c —— 泄漏成全局变量！
}

console.log(obj.a); // 3
console.log(c);     // 4 —— 意外的全局污染
```

`with` 在运行时把对象的属性动态变成一个「作用域层」，静态分析彻底失效。因此**严格模式直接禁止 `with`**（语法错误），`eval` 也被限制——现代代码里两者都不应出现。

## 回看开篇

| 步骤 | 发生了什么 |
|---|---|
| 定义 `foo` | `foo.[[Environment]]` ← 全局环境（定义时锁定） |
| 调用 `bar()` | 创建 bar 的环境，其中有 `value = 2` |
| `bar` 内调用 `foo()` | 创建 foo 的环境；查找 `value`：foo 自身（无）→ `[[Environment]]` 指向的**全局**（命中 1） |
| 输出 | `1` —— `bar` 的环境从头到尾不在查找路径上 |

一句话：**调用位置只决定「什么时候执行」，定义位置才决定「能看到什么」。**

## 实战延伸

**1. 函数作为参数传递时的经典变体 ⭐**

```js
var x = 10;

function print() {
  console.log(x);
}

function run(fn) {
  var x = 20;
  fn(); // 10 —— 不是 20！
}

run(print);
```

回调函数不管被传到哪里执行，作用域永远看定义处——这是理解「事件回调、定时器回调里的变量来源」的钥匙，也是第 5 篇《闭包》的全部前提。

**2. 词法作用域是闭包的地基**

既然函数带着「出生地证明」到处走，那么外层函数即使执行结束，它的环境也能被内层函数继续引用——这正是闭包延长变量生命周期的机制。下一篇《作用域链》会把查找路径完整画出来。

**3. 工程习惯**

- 回调、钩子函数依赖的外部变量，尽量在定义处可见、命名清晰，别依赖调用方「恰好」提供的同名变量；
- ESLint 的 `no-eval`、`no-with` 规则应默认开启。

## 总结

- 词法作用域 = 「定义时确定」，动态作用域 = 「调用时确定」；
- 机制核心：函数对象通过 `[[Environment]]` 在创建时锁定定义处的词法环境；
- 调用位置只影响执行时机，不影响变量可见性；
- `eval` 和 `with` 是词法作用域的破坏者，严格模式下被限制/禁止；
- 静态可分析性是词法作用域被主流语言选中的根本原因，也是前端工程化（tree-shaking、静态检查）的前提。

**面试一句话回答**：JavaScript 采用词法作用域——函数能访问哪些变量在定义时就通过内部槽 [[Environment]] 锁定了，与调用位置无关；所以 foo 在 bar 内被调用时，依然沿「定义处的全局环境」找到 value = 1，而不是 bar 里的 2。动态作用域才按调用栈查找，bash 那类语言是它的代表。
