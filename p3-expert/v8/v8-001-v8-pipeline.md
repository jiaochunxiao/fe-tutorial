# V8 之如何执行一段 JavaScript：解析、编译与执行

## 从「同一段代码为什么越跑越快」说起

> **系列导读**：《V8 与 JavaScript 底层系列》共 8 篇——从执行流水线到 JIT、隐藏类、GC 与内存排查，把「引擎视角的 JS」讲透（《v8-005 内存与 GC》已产出，本篇是系列的机制起点）。

```js
function add(a, b) { return a + b; }
for (let i = 0; i < 1e7; i++) add(i, i);
// 第 1 次调用：0.001ms；第 100 万次：0.0001ms —— 同一段代码，越跑越快？
```

答案藏在 V8 的执行流水线里：**同一函数会经历「解释执行 → 优化编译为机器码」的升级**。⭐⭐⭐ 本篇讲清 V8 从源码到执行的完整旅程——它是后续 JIT（003）、隐藏类（002）的地图。

## 现象与直觉解释

先回答一个认知前提：**CPU 不认识 JavaScript**——它只执行机器码。所以引擎必须把源码「翻译」成机器码，翻译策略决定了性能特征：

```
方案A 提前全量编译（AOT）：启动前全部翻好 —— 启动慢、内存大
方案B 逐句解释执行：每句现翻现执行 —— 启动快、跑得慢
方案C 混合（JIT）：先快速解释起步，热点代码再编译成机器码 —— 两头兼顾 ⭐
```

V8（以及所有现代 JS 引擎）选 C：**「快速起步 + 越跑越快」**。

## 深入原理：源码到执行的五站旅程 ⭐⭐⭐

### 第①站：词法/语法分析（Parser）——源码 → AST

```
"const x = 1 + 2;"
   │ 词法分析（Lexer）：切成 Token 流
   │   [const] [x] [=] [1] [+] [2] [;]
   ▼ 语法分析（Parser）：按文法组装
AST { type: 'VariableDeclaration', init: BinaryExpression(+, 1, 2), … }
（AST 是编译器通用中间表示 —— engineering-006 讲过它的工具链应用）
```

两个工程细节：**懒解析（lazy parsing）**——函数体先跳过只登记外壳（首次调用才细解析，加速启动）；**预解析器**快速跳过时的安全性检查。

### 第②站：Ignition 解释器——AST → 字节码并执行

```
AST ──▶ 字节码（Bytecode）—— 引擎自定义的「紧凑指令集」：
   Ldar a1        // 加载参数1
   Ldar a2        // 加载参数2
   Add            // 相加
   Return

Ignition 逐条解释执行字节码（自带字节码 ↔ 机器码的快速跳转表）
⚠️ 为什么不直接生成机器码？—— 字节码生成【极快】、体积小、可逐条执行：
   冷代码（只跑一两次的函数）用它执行，性价比最高
```

**这解释了「JS 启动快」**：不需要全量编译就能跑；也埋下伏笔——热代码值得更好的待遇。

### 第③站：热点探测——谁值得优化

```
Ignition 执行时顺手【数执行次数】（反馈向量 Feedback Vector）：
  某函数/循环的执行计数超过阈值（如 1000+ 次）→ 标记为【热点】
  同时记录运行时观测：add 的参数每次都是 Smi（小整数）？字符串？
  —— 这些观测将决定优化编译器怎么「对症下药」⭐（类型反馈）
```

### 第④站：TurboFan 优化编译器——字节码 + 类型反馈 → 机器码

```
TurboFan（ optimizing compiler）：
  输入：字节码 + 类型反馈（「add 总是收到两个小整数」）
  处理：基于反馈做激进的【投机优化】——按「小整数加法」生成机器指令
       （比通用加法——要判断 string/number/对象——快一个量级）
  输出：高度优化的机器码
⚠️ 投机的含义：假设是「猜」的 —— 猜错要有退路（下一站的 deopt）
```

**开篇之谜的答案**：循环到百万次时 add 早已被 TurboFan 优化成「两个整数相加」的几条机器指令——比解释执行快一个数量级。

### 第⑤站：Deopt（反优化）——猜错了怎么办 ⭐⭐

```js
function add(a, b) { return a + b; }
for (let i = 0; i < 1e6; i++) add(i, i);      // 热点 + 反馈「总是小整数」→ 优化
add('x', 'y');                                 // ⚠️ 参数类型变了！假设崩塌
// Deopt：抛弃优化机器码 → 回到 Ignition 字节码（正确性永远优先）
// 若继续变热 → 带着新反馈重新优化（更保守的类型假设）
```

**这就是「优化敏感代码」的根源**（003 篇展开）：参数类型忽变、给对象乱加属性等「破坏假设」的写法会反复触发 deopt——优化成果归零重来。

### 一张总图 ⭐

```
源码 ──Parser(懒解析)──▶ AST
   ──Ignition──▶ 字节码 ──解释执行──▶（执行计数+类型反馈）
                     │
              热点(>阈值) ──TurboFan──▶ 机器码（投机优化）──▶ 高速执行
                     ▲                                    │
                     └──────── 假设被打破：Deopt ◀────────┘
```

### 五站旅程里的三个「为什么」⭐⭐

1. **为什么有字节码这一层**（不 AST→机器码直翻）？——字节码是「生成快、可解释、可观测」的中间形态；直接编译全部代码到机器码会让启动灾难化；
2. **为什么优化要「投机」**？——JS 动态类型：通用加法要处理十几种组合；类型反馈让 TurboFan 只为「实际发生的组合」生成代码——快的前提是假设可被 deopt 撤销；
3. **为什么函数写小更友好**？——热点探测与优化以函数为单位：小函数快速变热被优化；巨型函数一次 deopt 全部报废。

## 回看开篇

「越跑越快」= JIT 的两段式：冷启动走 Ignition 字节码（秒起）→ 热点被 TurboFan 按类型反馈编译成机器码（飞快）→ 类型假设被打破时 deopt 回退保正确。**「先跑起来，再跑快，错了能回头」**——V8 流水线的设计哲学一句话。

## 实战延伸

**1. 面试答题骨架**：「V8 执行分五站——Parser 把源码解析成 AST（带懒解析加速启动）；Ignition 解释器生成并执行字节码，兼顾启动速度与内存；执行中收集类型反馈并计数，超过阈值的热点交给 TurboFan；TurboFan 依据类型反馈做投机优化生成机器码；假设被打破时触发 deopt 回退字节码保证正确性，之后可再次优化。字节码层的存在让冷代码无需全量编译，TurboFan 让热代码达到接近原生的速度。」

**2. 亲手观察**：Node 用 `--trace-opt --trace-deopt` 跑一个热点循环——终端直接打印 `[optimizing: add …]` 与 `[deoptimizing …]`，五站旅程肉眼可见。

**3. 一道认知题**：「为什么删掉 try-catch 不能『提速』了？」——现代 V8 的 try-catch 已不再阻碍优化（老引擎时代会）——引擎细节随版本演进，「过时的性能建议」要打问号。

## 图解总结

```
源码 → [Parser+懒解析] → AST → [Ignition] → 字节码 → 解释执行(带反馈收集)
                                                    │ 计数超阈值 + 类型反馈
                                              [TurboFan 投机优化]
                                                    ▼
                                              机器码(近乎原生速度)
                                                    │ 类型假设被打破
                                              [Deopt 回退字节码] ──▶ 可再优化
```

## 总结

- 五站流水线：Parser（AST+懒解析）→ Ignition（字节码+解释）→ 热点探测 → TurboFan（投机机器码）→ Deopt 兜底；
- 字节码层是启动速度与内存的关键中间态；
- 类型反馈是投机优化的依据——「实际怎么跑就怎么优化」；
- deopt 保证正确性优先；反复 deopt 是性能杀手（003 篇展开）；
- 小函数更容易被优化；过时的引擎建议要重新验证。

**面试一句话回答**：V8 执行 JavaScript 分五个阶段——解析器将源码解析为 AST，配合懒解析跳过暂不执行的函数体以加速启动；Ignition 解释器把 AST 编译成紧凑的字节码并逐条解释执行，使冷代码无需全量编译即可运行；执行过程中收集类型反馈与执行计数，超过阈值的热点函数交给 TurboFan 优化编译器；TurboFan 依据类型反馈做投机优化——例如参数一直是大整数就按整数加法生成机器码，性能接近原生；一旦运行时的实际情况与假设不符立即触发反优化，回退到字节码解释执行保证语义正确，之后可以带着新反馈重新优化。这套先解释后编译、错了能回退的流水线就是「越跑越快」的来源。
